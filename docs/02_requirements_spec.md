# 2.2 Разработка спецификации требований к программному средству

## 2.2.1 Общие сведения

**Наименование системы:** Платформа проведения онлайн-олимпиад с системой прокторинга (Olympiad Proctoring Platform)

**Назначение:** Автоматизация процесса создания, проведения и проверки онлайн-олимпиад с контролем честности выполнения заданий участниками.

**Пользователи системы:**
- Студенты — участники олимпиад
- Организаторы — создатели и администраторы олимпиад
- Администраторы — управление пользователями системы

---

## 2.2.2 Назначение и цели создания системы

**Цель разработки:** Создание веб-приложения, позволяющего:
1. Организаторам создавать и публиковать олимпиады с различными типами вопросов
2. Студентам проходить олимпиады в контролируемой среде
3. Автоматически обнаруживать подозрительную активность во время выполнения заданий
4. Автоматизировать проверку ответов и подсчёт результатов

---

## 2.2.3 Функциональные требования

### 2.2.3.1 Модуль аутентификации и управления пользователями

| Код | Требование | Описание |
|-----|-----------|----------|
| FR-01 | Регистрация пользователя | Система должна обеспечивать регистрацию новых пользователей по email/паролю или через Google OAuth 2.0 |
| FR-02 | Аутентификация | Система должна выполнять вход пользователя с выдачей JWT access token (1 час) и refresh token (24 часа) |
| FR-03 | Обновление токена | Система должна автоматически обновлять access token при его истечении через refresh token |
| FR-04 | Управление профилем | Пользователь должен иметь возможность редактировать имя, фамилию и привязывать Telegram для уведомлений |
| FR-05 | Ролевая модель | Система должна поддерживать три роли: STUDENT, ORGANIZER, ADMIN с разграничением доступа |
| FR-06 | Управление пользователями (ADMIN) | Администратор должен иметь возможность просматривать, создавать, редактировать, блокировать и удалять пользователей |
| FR-07 | Смена роли (ADMIN) | Администратор должен иметь возможность изменять роль любого пользователя |

### 2.2.3.2 Модуль управления олимпиадами

| Код | Требование | Описание |
|-----|-----------|----------|
| FR-08 | Создание олимпиады | Организатор должен иметь возможность создать олимпиаду в статусе черновика с указанием названия, описания, длительности и временного окна проведения |
| FR-09 | Редактирование олимпиады | Организатор должен иметь возможность изменять параметры олимпиады до её публикации |
| FR-10 | Публикация олимпиады | Организатор должен иметь возможность опубликовать олимпиаду, после чего она становится доступна студентам |
| FR-11 | Удаление олимпиады | Администратор должен иметь возможность удалить олимпиаду |
| FR-12 | Просмотр списка олимпиад | Система должна отображать список олимпиад с фильтрацией по статусу и поиском по названию |
| FR-13 | Жизненный цикл олимпиады | Система должна поддерживать статусы: DRAFT → PUBLISHED → ACTIVE → FINISHED/CANCELLED |
| FR-14 | Календарь праздников | Организатор должен видеть предупреждение при выборе даты, совпадающей с государственными праздниками (Nager.Date API) |

### 2.2.3.3 Модуль управления вопросами

| Код | Требование | Описание |
|-----|-----------|----------|
| FR-15 | Добавление вопроса | Организатор должен иметь возможность добавлять вопросы в олимпиаду |
| FR-16 | Типы вопросов | Система должна поддерживать типы: SINGLE_CHOICE, MULTIPLE_CHOICE, TEXT, CODE, MANUAL_REVIEW |
| FR-17 | Редактирование вопроса | Организатор должен иметь возможность изменять текст, варианты ответов и правильный ответ |
| FR-18 | Удаление вопроса | Организатор должен иметь возможность удалять вопросы |
| FR-19 | Балльная система | Каждый вопрос должен иметь указание максимального количества баллов |

### 2.2.3.4 Модуль участия в олимпиаде

| Код | Требование | Описание |
|-----|-----------|----------|
| FR-20 | Регистрация на олимпиаду | Студент должен иметь возможность зарегистрироваться для участия в опубликованной олимпиаде |
| FR-21 | Начало выполнения | Студент должен иметь возможность начать выполнение заданий, после чего запускается индивидуальный таймер |
| FR-22 | Отображение вопросов | Система должна последовательно отображать вопросы участнику |
| FR-23 | Сохранение ответов | Система должна сохранять ответы студента (выбор вариантов, ввод текста, написание кода) |
| FR-24 | Выполнение кода | Система должна предоставлять возможность запуска кода через Judge0 CE и просмотра результата |
| FR-25 | Загрузка файлов | Студент должен иметь возможность прикреплять файлы (до 10 МБ: JPEG, PNG, GIF, PDF, DOC, DOCX, XLS, XLSX) |
| FR-26 | Автоматическое завершение | Система должна автоматически завершать участие при истечении таймера |
| FR-27 | Досрочное завершение | Студент должен иметь возможность досрочно завершить выполнение |
| FR-28 | Подсчёт результатов | Система должна автоматически подсчитывать баллы: за правильные ответы, с учётом ручной проверки и вычета за нарушения |

### 2.2.3.5 Модуль прокторинга (антисписывания)

| Код | Требование | Описание |
|-----|-----------|----------|
| FR-29 | Полноэкранный режим | Система должна принудительно переводить браузер студента в полноэкранный режим при старте |
| FR-30 | Отслеживание переключения вкладок | Система должна фиксировать каждое переключение на другую вкладку браузера (TAB_SWITCH) |
| FR-31 | Отслеживание выхода из fullscreen | Система должна фиксировать выход из полноэкранного режима (FULLSCREEN_EXIT) |
| FR-32 | Отслеживание неактивности | Система должна фиксировать отсутствие активности мыши/клавиатуры более 60 секунд (INACTIVITY) |
| FR-33 | Локальное хранение событий | Система должна сохранять события прокторинга в localStorage как резервную копию |
| FR-34 | Передача событий на сервер | Система должна отправлять события прокторинга на сервер вместе с ответами |
| FR-35 | Расчёт подозрительности | Система должна вычислять weightedScore: TAB_SWITCH×5 + FULLSCREEN_EXIT×3 + INACTIVITY×0.5 |
| FR-36 | WebSocket-трансляция | Система должна передавать события прокторинга в реальном времени через WebSocket |

### 2.2.3.6 Модуль проверки и результатов

| Код | Требование | Описание |
|-----|-----------|----------|
| FR-37 | Ручная проверка | Организатор должен иметь возможность вручную оценивать ответы типа MANUAL_REVIEW с комментарием |
| FR-38 | Просмотр результатов | Студент должен иметь возможность просматривать свои результаты после завершения |
| FR-39 | История участий | Студент должен иметь возможность просматривать историю всех своих олимпиад |
| FR-40 | Таблица участников | Организатор должен видеть список участников с баллами, статусом и временем |
| FR-41 | Аналитика прокторинга | Организатор должен видеть аналитику нарушений по каждому участнику |

### 2.2.3.7 Модуль уведомлений (Telegram)

| Код | Требование | Описание |
|-----|-----------|----------|
| FR-42 | Привязка Telegram | Пользователь должен иметь возможность привязать Telegram-аккаунт для получения уведомлений |

### 2.2.3.8 Модуль выполнения кода

| Код | Требование | Описание |
|-----|-----------|----------|

## 2.2.4 Нефункциональные требования

### 2.2.4.1 Требования к архитектуре и технологиям

| Код | Требование | Описание |
|-----|-----------|----------|
| NFR-01 | Архитектура | Система должна быть построена по клиент-серверной архитектуре с REST API |
| NFR-02 | Backend | Серверная часть должна быть реализована на Java 21 с использованием Spring Boot 3 |
| NFR-03 | Frontend | Клиентская часть должна быть реализована на React 18 с TypeScript |
| NFR-04 | База данных | В качестве СУБД должна использоваться PostgreSQL 15 |
| NFR-05 | Кэширование | Для кэширования и хранения сессий должен использоваться Redis 7 |
| NFR-06 | Контейнеризация | Система должна разворачиваться через Docker Compose |

### 2.2.4.2 Требования к безопасности

| Код | Требование | Описание |
|-----|-----------|----------|
| NFR-07 | Аутентификация | Доступ к API должен осуществляться по JWT токенам |
| NFR-08 | Хеширование паролей | Пароли должны храниться в хешированном виде (BCrypt) |
| NFR-09 | Авторизация | Доступ к функциям должен контролироваться на основе ролей (RBAC) |
| NFR-10 | Stateless | Сервер не должен хранить состояние сессии |

### 2.2.4.3 Требования к производительности

| Код | Требование | Описание |
|-----|-----------|----------|
| NFR-11 | Время ответа API | Среднее время ответа API не должно превышать 500 мс |
| NFR-12 | Одновременные участники | Система должна поддерживать не менее 100 одновременных участников |
| NFR-13 | Точность таймера | Таймер обратного отсчёта должен синхронизироваться с серверным временем |

### 2.2.4.4 Требования к интерфейсу

| Код | Требование | Описание |
|-----|-----------|----------|
| NFR-14 | Адаптивность | Интерфейс должен корректно отображаться на desktop-разрешениях (1920×1080 и выше) |
| NFR-15 | Русский язык | Интерфейс системы должен быть на русском языке |
| NFR-16 | Индикация таймера | Таймер обратного отсчёта должен быть виден на странице выполнения постоянно |

### 2.2.4.5 Требования к надёжности

| Код | Требование | Описание |
|-----|-----------|----------|
| NFR-17 | Резервное копирование | События прокторинга должны дублироваться в localStorage при недоступности сервера |
| NFR-18 | Миграции БД | Изменения схемы базы данных должны выполняться через Flyway-миграции |
| NFR-19 | Обработка ошибок | Система должна корректно обрабатывать и логировать ошибки на стороне сервера |

## 2.2.5 Модель данных (сущности)

| Сущность | Назначение | Ключевые атрибуты |
|----------|-----------|-------------------|
| User | Пользователь системы | id, email, passwordHash, fullName, role, isActive |
| Olympiad | Олимпиада | id, title, description, startTime, endTime, durationMinutes, status |
| Question | Вопрос олимпиады | id, text, type, options, correctAnswer, points |
| Participation | Участие студента | id, userId, olympiadId, startedAt, finishedAt, score, status |
| Answer | Ответ на вопрос | id, participationId, questionId, answer, isCorrect, pointsEarned |
| ProctoringEvent | Событие прокторинга | id, userId, olympiadId, eventType, metadata, timestamp |
| FileAttachment | Прикреплённый файл | id, answerId, fileName, originalName, mimeType, size, url |
| RefreshToken | Токен обновления | id, userId, token, expiresAt, revoked |
